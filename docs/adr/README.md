## 🔄 使用与演进

一个ADR只记录一个重要决定。状态采用Proposed、Accepted、Rejected、Superseded；被替代记录保留原理由并链接后继记录。Accepted表示采用方案，不代表所有目标已经实现；实现和验证另行记录。

旧`ADR-S4-001`至`ADR-S4-007`保留在内部Stage4原始归档，属于当时设计意图；本轮不将尚未全局实现的目标自动宣称为现状。编号不复用。

后续复用[TEMPLATE](TEMPLATE.md)。仅在改变模块边界、数据语义、状态/资源所有权、依赖或发布边界时新增ADR；普通局部修改不要求ADR。

审核可直接纠正笔误、补清已有决策的接口和限制，并标注修订日期及范围；不借澄清改写Accepted的原取舍。改变已接受决定时另建ADR并保留替代关系。Proposed可在审核中调整；“审核完成”“采用决定”“实现验收通过”分别记录。

## 🧑‍🏫 怎样在日常开发中使用

ADR是Architecture Decision Record（架构决策记录）。它回答“为什么选择这条路”，帮助以后改功能时理解当时约束。一个决定通常一页就够；不用为按钮颜色、改错别字等普通改动建立ADR。

本次[ADR-0003](0003-search-boundaries.md)就是例子：用户需要找文件和找变量；我们考虑统一跨文件索引、仅过滤树、两个入口三种方案，决定先按文件名查目录，再查当前已打开文件的变量。记录还说明线程归谁、关闭文件后如何使结果失效，以及将来增加跨文件内容扫描时为什么需要复审。

1. **编码前**：遇到重要取舍，复制模板，写背景、真实备选方案和决定。尚未确定用Proposed；已决定采用用Accepted。
2. **编码时**：让接口和所有权遵循决定；需求变化时先检查原约束是否仍成立。任务卡另记代码进度和验收证据。
3. **完成时**：核对实现符合决定。Accepted只表示“采用这个方案”，通过测试和完成日期仍写在任务卡。
4. **以后改变时**：不抹掉旧理由。另建下一编号ADR，解释新条件，在旧记录标Superseded并相互链接。Rejected方案也保留，避免反复讨论同一问题。

简单分工：**ADR写为什么，现行契约写现在接口是什么，任务卡写做什么和验收结果，Changelog写完成了什么。**新成员接手时先读当前模块契约，需要理解取舍时再读对应ADR。

## 📚 方法来源

采用背景、备选、决定、后果和复审条件的轻量结构。本项目沿用户已有授权实施；ADR记录理由，任务卡记录实际完成情况。
